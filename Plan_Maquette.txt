PLAN FINAL DE LA MAQUETTE - PROJET 11 : BIOLAB ANALYTICS
====================================================
Version 4 - Document "as-built" : reflete l'implementation Terraform/Docker



0. WORKFLOW METIER DE REFERENCE (du depot hopital a la livraison)
----------------------------------------------------
Inchange depuis la version 3 - c'est la colonne vertebrale que chaque
composant code doit permettre de derouler reellement, et c'est desormais
verifiable en pratique (voir OPERATIONS_MANUAL.md, section 5).

  1. INTAKE - L'hopital depose le fichier genetique sur le serveur SFTP
     (dossier d'entree dedie).
  2. ENREGISTREMENT ADMINISTRATIF - Le poste admin cree/retrouve le patient
     et le dossier medical, genere un CODE-BARRES, cree une facture
     "en_attente".
  3. TRANSMISSION - Le fichier est recupere via SFTP par l'admin et etiquete
     uniquement par le code-barres (jamais l'identite), depose dans un
     volume "handoff" partage avec le bio-informaticien.
  4. ANALYSE - Le bio-informaticien soumet le fichier au noeud de calcul ;
     le resultat brut (meme code-barres) est pousse automatiquement vers
     MinIO.
  5. ATTRIBUTION - Le technicien scanne le code-barres dans le LIMS, qui
     ecrit directement dans patient-db.
  6. VALIDATION MEDICALE - Le biologiste valide via le LIMS.
  7. PREPARATION ENVOI - L'admin recupere le resultat valide depuis MinIO et
     le depose, via SFTP reel, dans le dossier "to_encrypt" du serveur SFTP.
  8. CHIFFREMENT MAISON - Le watcher (conteneur autonome, aucune action
     manuelle) chiffre automatiquement et depose dans "outbound".
  9. ENVOI - L'hopital recupere le fichier chiffre via SFTP reel (meme cle
     partagee que l'admin).
  10. CLOTURE - L'admin verifie via SFTP que le fichier est bien la, puis
      statut -> "livre", facture -> "envoyee".

Cette version confirme que l'integralite du workflow est EXECUTABLE de bout
en bout via des commandes reelles (docker exec + interface web LIMS), sans
aucune intervention manuelle sur le systeme de fichiers hote - voir
OPERATIONS_MANUAL.md pour le mode d'emploi complet.


1. RESEAUX DOCKER (implementation reelle)
----------------------------------------------------
- net-sci-admin (10.10.1.0/24) : noeud de calcul, MinIO, LIMS, patient-db,
  automate, homemade-crypto, les 5 postes utilisateurs, Adminer.
- net-it (10.10.2.0/24) : LDAP, phpLDAPAdmin, bastion+logs (IP statique
  10.10.2.10).
- net-dmz (10.10.3.0/24) : serveur SFTP, pare-feu.
- net-external (10.10.4.0/24) : hopital, ancien prestataire, attaquant,
  clinique/recherche/pharma (placeholders).

AJUSTEMENT DOCUMENTE : LDAP et bastion+logs sont dual-homes (net-it +
net-sci-admin) avec IP statique sur ce dernier (10.10.1.10), car de
nombreux services doivent les joindre pour authentifier/journaliser. Le
poste admin, l'hopital et l'ancien prestataire sont EGALEMENT dual-homes
directement sur net-dmz (en plus de leur reseau d'origine), en attendant
une refonte reseau plus poussee - consequence : ces flux-la NE PASSENT PAS
par le pare-feu (section 11), qui ne controle reellement que l'acces
publie sur l'hote (voir section 11).


2. LDAP / IAM (implemente)
----------------------------------------------------
OpenLDAP + phpLDAPAdmin (port 8081, sans restriction). 5 comptes reels,
CHACUN avec un mot de passe DIFFERENT mais faible (biologiste1/Bio2024!,
bioinfo1/Genome99, technicien1/Labo1234, admin1/Accueil2023,
it1/Support01), tous dans un seul groupe plat "employees" (conserve tel
que valide). Bind anonyme REELLEMENT DESACTIVE (olcDisallows: bind_anon sur
cn=config) : toute connexion doit s'authentifier. Chaque poste utilisateur
effectue un vrai bind LDAP au demarrage de son conteneur.


3. NOEUD DE CALCUL + STOCKAGE (implementes)
----------------------------------------------------
Noeud de calcul : appli Flask reelle (port 5000, HTTP simple), parse un
fichier FASTA, calcule longueur de sequence / taux GC / un pseudo-variant
deterministe, pousse automatiquement le resultat JSON vers MinIO (bucket
raw-results) sous le meme code-barres.
Stockage : MinIO, desormais en HTTPS avec le certificat auto-signe emis par
la CA interne (section 12) ; le client du noeud de calcul s'y connecte
volontairement SANS verifier ce certificat (verify=False code en dur) -
faille PKI documentee et reellement codee, pas seulement decrite.


4. LIMS (implemente)
----------------------------------------------------
Appli Flask servie en HTTPS (port 5001, certificat auto-signe verifiable
via pki/ca.crt). Ecrit DIRECTEMENT dans patient-db (pas de base separee,
fusion actee en v3). Deux ecrans proteges par authentification LDAP reelle :
/assign (role technicien) et /validate (role biologiste). La separation des
roles est verifiee UNIQUEMENT via la table applicative patient-db.app_users
(LDAP lui-meme ne distingue rien, groupe plat) - faille documentee et
assumee. Aucun hash/signature entre attribution et validation - egalement
assume et signale a l'ecran de validation lui-meme.


5. CHIFFREMENT MAISON + SFTP (implementes, bidirectionnels)
----------------------------------------------------
Chiffrement maison : conteneur autonome, surveille en continu un dossier
partage (volume Docker "exchange"), chiffre (XOR statique, cle codee en
dur, sans IV/sel) tout fichier depose dans to_encrypt/, depose le resultat
dans outbound/. XOR etant involutif, chiffrement = dechiffrement - point
fort a demontrer dans le rapport de risque.

Serveur SFTP : image maison (pas une image toute faite), sshd configure en
chroot par utilisateur, authentification PAR CLE UNIQUEMENT. Reellement
BIDIRECTIONNEL : dossier inbound/ (hopital ecrit, admin lit via groupe Unix
partage) et outbound/ (admin/watcher ecrivent, hopital lit). Permissions
Unix reelles avec UID/GID fixes coherents entre les images serveur SFTP et
watcher.

FAILLE MAJEURE REELLEMENT CODEE : les comptes biolab_admin ET
hopital_saint_martin utilisent LA MEME paire de cles SSH generee une seule
fois (jamais renouvelee). De plus, une SECONDE cle - celle d'un ancien
prestataire externe charge historiquement du chiffrement maison - a ete
ajoutee aux authorized_keys de biolab_admin et n'a jamais ete retiree :
acces residuel reellement exploitable (voir section 8, "ancien
prestataire").


6. POSTES UTILISATEURS (implementes, 5 roles)
----------------------------------------------------
Une SEULE image Docker commune ("poste de travail standard"), differenciee
uniquement par l'identite LDAP injectee et les volumes montes. Chaque poste
effectue un VRAI bind LDAP au demarrage (echoue bruyamment si les
identifiants sont faux - plus aucun chemin anonyme).
- Poste admin : 4 scripts reels utilisant du vrai SFTP (paramiko) - intake
  (creation patient/dossier/facture), recuperation inbound, preparation
  d'envoi (refuse si statut != valide), confirmation de livraison.
- Poste bio-informaticien : soumission reelle au noeud de calcul depuis le
  volume "handoff" partage avec l'admin.
- Postes technicien / biologiste : authentification LDAP prouvee ;
  l'interaction metier se fait via l'interface web du LIMS (navigateur).
- Poste IT : script de demonstration Modbus (section 9).


7. AUTOMATE DE LABORATOIRE (implemente)
----------------------------------------------------
Serveur Modbus TCP reel (pymodbus), registres simules (compteur
d'echantillons, temperature, statut machine, capteur de porte) qui
evoluent en continu via un thread de simulation. AUCUNE authentification
(le protocole Modbus TCP n'en a nativement pas), place sur le reseau plat
net-sci-admin. Script de demonstration fourni, executable depuis n'importe
quel poste du meme reseau, prouvant la lecture ET l'ecriture sans aucun
identifiant.


8. PARTIES PRENANTES EXTERNES (implementees)
----------------------------------------------------
- Hopital partenaire : flux SFTP bidirectionnel COMPLET et reel (memes
  scripts que le poste admin, meme cle partagee - faille documentee :
  BioLab ne peut pas revoquer l'acces de l'hopital sans casser son propre
  acces admin).
- Ancien prestataire externe : conteneur dedie qui se connecte REELLEMENT
  au serveur SFTP en tant que biolab_admin, via une cle jamais revoquee
  depuis la fin de son contrat. Script de demonstration qui liste le
  contenu accessible et rappelle explicitement les privileges obtenus.
- Attaquant generique : conteneur minimal (nmap, curl, client ssh, dig),
  volontairement isole sur net-external uniquement (pas de rattachement a
  la DMZ), pour que le pare-feu (section 11) ait un perimetre reel a
  demontrer, contrairement a l'hopital/admin rattaches pragmatiquement.
- Clinique / centre de recherche / entreprise pharmaceutique : placeholders
  legers (conteneurs Alpine inactifs), conformement au plan valide.


9. BASE DE DONNEES PATIENTS + FACTURATION (implementees)
----------------------------------------------------
Postgres, schema complet (patients, hopitaux, dossiers_medicaux, resultats,
factures, app_users). Cycle de statut du dossier aligne sur le workflow
(recu -> en_analyse -> attribue -> valide -> chiffre -> livre). Facturation
reellement geree (en_attente -> envoyee), consultable/modifiable via
ADMINER, expose SANS RESTRICTION sur le reseau interne (port 8082) - faille
volontaire supplementaire, conforme au plan.


10. JOURNALISATION (implementee)
----------------------------------------------------
Le pilote de journalisation natif Docker (log_driver=syslog) envoie
REELLEMENT les logs de LDAP, phpLDAPAdmin, patient-db, MinIO, noeud de
calcul, LIMS, chiffrement maison et des 5 postes utilisateurs vers le
serveur de logs central, via UDP/514 NON CHIFFRE et NON AUTHENTIFIE - IP
statique utilisee (10.10.1.10) car la resolution de nom ne fonctionne pas
depuis le contexte du daemon Docker. Fichier plat unique, aucune correlation
ni alerte - base pour la recommandation future d'un vrai SIEM (rapport
d'analyse de risque, pas implemente ici).
LIMITE DOCUMENTEE : le serveur SFTP (DMZ) et les parties prenantes
externes n'envoient PAS leurs logs ici (aucune route reseau etablie vers
le serveur de logs) - un angle mort de supervision volontairement laisse
tel quel et a signaler dans le rapport.


11. BASTION + SERVEUR DE LOGS (implementes, FUSIONNES)
----------------------------------------------------
AJUSTEMENT DOCUMENTE : le plan initial decrivait deux machines distinctes.
Dans l'implementation, bastion et serveur de logs sont LE MEME conteneur -
patient-db et LDAP n'etant pas eux-memes des serveurs SSH, "rebondir" via
SSH depuis le bastion n'aurait aucun sens ; le bastion sert donc de poste
d'atterrissage SSH (cle dediee, port hote 2200) equipe des outils
d'administration (psql, ldap-utils) pour agir directement sur ces services
depuis cette session. Faille a noter pour le rapport : compromettre cette
seule machine donne a la fois le point d'administration ET l'integralite
de la piste d'audit.


12. PKI / CERTIFICATS (implementee, AUTO-SIGNEE - point important valide)
----------------------------------------------------
Une autorite de certification interne REELLE mais AUTO-SIGNEE ("BioLab
Analytics Internal CA") a ete generee (script reproductible fourni), qui
signe a son tour deux certificats serveur reels : LIMS et MinIO. Ce n'est
PAS une PKI d'entreprise geree (pas d'intermediaire, pas de CRL/OCSP, cle
de la CA rangee au meme endroit que les cles serveur) - exactement le
niveau de maturite documente dans le plan. VERIFICATION REELLE effectuee
sur le flux poste technicien/biologiste -> LIMS (script de demonstration
fourni) ; VERIFICATION VOLONTAIREMENT DESACTIVEE sur le flux noeud de
calcul -> MinIO. Les deux comportements sont reellement codes, pas
seulement decrits.


13. PARE-FEU (implemente, perimetre reellement applique mais limite)
----------------------------------------------------
Conteneur dedie, capacite NET_ADMIN, ip_forward active, regles iptables
REELLES et inspectables (iptables -L). Possede desormais le port hote 2222
et le redirige (DNAT) vers le serveur SFTP ; tout le reste est DROP par
defaut (filtrage minimal, regle ANSSI 25). LIMITE ASSUMEE ET DOCUMENTEE :
comme le poste admin et l'hopital sont deja directement rattaches a
net-dmz (section 1), leur trafic ne transite PAS par ce pare-feu - Docker
ne route pas automatiquement le trafic entre conteneurs d'un meme reseau
via un tiers sans reconfiguration reseau plus lourde (macvlan, routes
statiques), jugee hors perimetre raisonnable pour cette maquette. Ce
pare-feu controle neanmoins reellement le SEUL chemin qui n'etait
auparavant filtre par rien du tout (l'acces publie sur l'hote) - progres
reel, pas un decor.


14. RECAPITULATIF DE TOUS LES AJUSTEMENTS D'IMPLEMENTATION
----------------------------------------------------
1. LDAP : mots de passe individualises (plus de mot de passe unique
   partage), bind anonyme reellement desactive - suite a ta demande
   explicite en cours de projet.
2. Admin + hopital + ancien prestataire dual-homes directement sur
   net-dmz (limite Docker, documentee au lieu d'etre cachee).
3. PKI reellement generee et cablee (pas seulement prevue) : verification
   reelle sur un flux, desactivee sur un autre, comme demande.
4. Bastion et serveur de logs fusionnes en un seul conteneur (adaptation
   pragmatique face a l'absence de serveurs SSH sur patient-db/LDAP).
5. Journalisation via le pilote syslog natif de Docker plutot qu'un code
   applicatif dedie a chaque service - plus simple, tout aussi reel.
6. Pare-feu au perimetre volontairement restreint (le flux SFTP publie sur
   l'hote), pas l'integralite du trafic inter-reseaux - limite Docker
   documentee plutot que contournee en silence.
7. Automate Modbus et facturation/Adminer ajoutes tels quels, conformes au
   plan initial, sans adaptation necessaire.
8. Manuel d'exploitation redige (OPERATIONS_MANUAL.md) documentant chaque
   point d'acces, chaque identifiant, et la procedure complete de bout en
   bout.
